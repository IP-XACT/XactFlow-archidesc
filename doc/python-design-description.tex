\section{Introduction}

This document specifies a new \code{XactFlow} \code{Importer}: a way to describe a
design's architecture (which IPs it instantiates, how they're wired together over buses,
any ad hoc signal connections, and the ports and bus interfaces it offers to the outside)
as a plain Python script, instead of hand-written IP-XACT XML. Running the script produces
an \code{ipxact.Design} object and the \code{ipxact.Component} containing it, which the
rest of \code{XactFlow} already knows what to do with: \code{link()} resolves and checks
the design against a \code{Library}, and \code{XactFlow-design} and
\code{XactFlow-component} can serialize them back out to real IP-XACT \code{design} and
\code{component} XML documents.

This builds on the design description concept from \emph{IP-XACT-Based SoC Generation:
Tools and SoCMake Integration} (M.~Travaillard, B.~Denkinger, August 2026), specifically
its Section 4.3 and the \code{design2ipxact} transformation of Section 5.2. That transformation
scoped a full SoCMake-integrated pipeline (\code{sv2ipxact}, \code{design2ipxact},
\code{ipxact2sv}, a shared bus library, radiation-hardening hooks, CMake integration);
this document only covers the piece of it that becomes a standalone \code{XactFlow}
\code{Importer}, with no SoCMake or CMake dependency, consistent with every other
\code{XactFlow} plugin.

\section{Scope}

What this importer does:

\begin{enumerate}
    \item Execute a Python script that declares IP instances, top-level ports and bus
    interfaces, bus connections, and ad hoc connections using the API below.
    \item Resolve each IP reference to a real \code{ipxact.Component} via a
    \code{Library} the script itself provides.
    \item Build the corresponding \code{ipxact.Design} object: one
    \code{ComponentInstance} per IP instance, one \code{Interconnection} per bus
    connection (a \code{MonitorInterconnection} when one side is a monitor), one
    \code{AdHocConnection} per ad hoc connection. A top-level bus interface is reached
    with a \code{hierInterface}, a top-level port with an \code{externalPortReference}.
    \item Build the \code{ipxact.Component} containing the design: its top-level ports and
    bus interfaces, and a view instantiating the design through a
    \code{designInstantiation}.
\end{enumerate}

What it deliberately does not do, because \code{XactFlow} already does it elsewhere:

\begin{itemize}
    \item \textbf{Bus protocol compatibility checking.} \code{connect\_bus()} only
    matches interfaces by bus type and interface mode (see below); it does not
    check signal-level compatibility, that's \code{xactflow.link()}'s job, via its
    interconnection-compatibility SCR checks, run after this importer hands off the
    \code{Design}.
    \item \textbf{Address conflict checking, memory map validation.} Out of scope for the
    reasons in Section~\ref{sec:address-mapping}.
    \item \textbf{Anything else IP-XACT's semantic consistency rules cover.} This
    importer's only job is producing a syntactically well-formed \code{Design}; whether
    that \code{Design} is semantically sound, correct cross-references, compatible
    interfaces, valid addressing, sound hierarchy, and so on, is \code{SCR}'s job,
    unchanged from how every other \code{Design} (hand-written or otherwise imported) is
    checked today.
\end{itemize}

\section{The \texttt{Design} object}

\begin{lstlisting}[style=pyblock, caption={The \texttt{Design} API surface.}]
class Design:
    def __init__(self, vlnv: str, library: xactflow.Library) -> None: ...
    def add_ip(self, instance_name: str, vlnv: str, parameters: dict[str, object] | None = None, transforms: list[str] | None = None) -> IPInstance: ...
    def connect_bus(self, a: IPInstance | BusInterfaceRef, b: IPInstance | BusInterfaceRef, *, base_addr: int | None = None, size: int | None = None) -> None: ...
    def connect(self, source: PortRef, target: PortRef) -> None: ...
    def add_port(self, direction: str, name: str, width: int | None = None, *, connect: PortRef | None = None) -> PortRef: ...
    def add_bus(self, name: str, bus_type: str, mode: str, *, group: str | None = None, connect: IPInstance | BusInterfaceRef | None = None) -> BusInterfaceRef: ...
    def build(self) -> ipxact.Design: ...
    def build_component(self) -> ipxact.Component: ...
\end{lstlisting}

\subsection{\texttt{Design(vlnv, library)}}

\begin{itemize}
    \item \code{vlnv}: a colon-separated \code{"vendor:library:name:version"} string
    naming what the script describes. The two documents it produces need their own
    VLNVs: the component containing the design gets \code{.component} appended to the
    name, and the design \code{.design}, so \code{"example.org:soc:example:0.1"} gives
    \code{example.org:soc:example.component:0.1} and
    \code{example.org:soc:example.design:0.1}. Parsed eagerly; a malformed string (not
    exactly 4 fields) raises \code{ValueError} at construction.
    \item \code{library}: an already-scanned \code{xactflow.Library}. The script builds
    this itself (\code{Library.scan(...)}) and passes it in, \code{Design} never
    constructs or owns a \code{Library} implicitly. This keeps the script fully
    self-contained.
\end{itemize}

\subsection{\texttt{add\_ip(instance\_name, vlnv, parameters=None, transforms=None) -> IPInstance}}

Declares one component instance and resolves it immediately, not deferred to
\code{build()}:

\begin{itemize}
    \item \code{instance\_name} must follow the IP-XACT naming rule: it starts with a letter
    or \code{\_}, not a digit, followed by letters, digits, \code{\_}, \code{.} or
    \code{-}. It must also be unique within the design. A duplicate raises
    \code{ValueError} immediately, naming both the new call and the earlier one that
    already used it.
    \item \code{vlnv} is resolved against \code{library} right away. An unresolvable VLNV
    raises \code{ValueError} at the \code{add\_ip()} call site, not at the end of the
    script, so a mistake is reported on the line that made it.
    \item \code{parameters} maps a parameter's \textbf{name} (as declared on the resolved
    component) to an override value. This is IP-XACT's own \code{configurableElementValues}
    feature. For each entry, \code{add\_ip} looks up the matching \code{Parameter} by name
    on the resolved component:
    \begin{itemize}
        \item Unknown name: \code{ValueError}, naming the instance, the bad key, and the
        parameter names that \emph{are} available on that component.
        \item Name matches a parameter that cannot be overridden: \code{ValueError}. It
        needs a \code{parameterId} and \code{resolve="user"}. The standard says an
        \code{immediate} parameter (the default) cannot be modified through configuration.
        This is a defect in the referenced \emph{component} file, not something this importer
        can paper over (see Section~\ref{sec:relationship-sv} for why this matters in
        practice).
        \item Empty or blank value, or a float that is not finite (\code{nan}, \code{inf}):
        \code{ValueError}, since it is not a usable expression.
        \item Otherwise, the override is recorded against that parameter's
        \code{parameterId}.
    \end{itemize}
    \item \code{transforms} names zero or more transformations to apply to this
    instance, radiation hardening being one example. This importer does not apply them.
    It only records the names, in order, as a vendor extension on the resulting component
    instance.
    A separate tool, a transformer, does the work later. It takes the
    \code{ipxact.Design}, applies the transformations its instances ask for, and returns
    the modified \code{ipxact.Design}, ready for linking. A transformer can be kept
    private, and can be turned on or off without changing the design description.
\end{itemize}

Returns an \code{IPInstance} handle (see below) used to build bus and ad hoc connections
against this instance.

\subsubsection{\texttt{IPInstance}}

A handle returned by \code{add\_ip()}, carrying the instance name and the resolved
\code{ipxact.Component}.

\begin{lstlisting}[style=pyblock, caption={The \texttt{IPInstance} handle.}]
class IPInstance:
    name: str
    component: ipxact.Component

    def port(self, name: str) -> PortRef: ...
    def bus(self, name: str) -> BusInterfaceRef: ...
\end{lstlisting}

\begin{itemize}
    \item \code{.port(name)} looks up \code{name} in \code{component.model.ports};
    unknown name raises \code{ValueError} listing the ports that do exist. Used to build
    ad hoc connections.
    \item \code{.bus(name)} looks up \code{name} in \code{component.bus\_interfaces};
    unknown name raises \code{ValueError} the same way. Used only when
    \code{connect\_bus()} needs help picking the right bus (see below).
    \item \code{instance.some\_port} is a shorthand for \code{instance.port("some\_port")}.
    If a port has the same name as an \code{IPInstance} attribute, such as \code{name},
    use \code{.port(...)} instead.
\end{itemize}

\subsection{\texttt{connect\_bus(a, b, *, base\_addr=None, size=None)}}

Connects one bus interface on \code{a} to one bus interface on \code{b}. Each argument is
either a plain \code{IPInstance} (pick one of its bus interfaces automatically) or an
\code{IPInstance.bus(name)} (use that exact one). Here is how it picks:

\begin{enumerate}
    \item For each side, the candidates are: the exact interface given, if a
    \code{bus(name)} was passed; otherwise every initiator or target interface on that
    instance's component that an earlier \code{connect\_bus()} call has not already used.
    \item A pair \code{(interface\_a, interface\_b)} matches if they share the same bus
    type, and their \code{mode}s are opposite. The same bus type means the same bus
    definition, or one that \code{extends} the other, directly or not (SCR 2.2), and the
    same parameter values set on it (\code{bus\_type.config\_element\_values}), compared
    after evaluation. The modes that connect are the ones the standard allows: initiator with
    target or mirrored initiator, mirrored target with target, and system with mirrored
    system of the same \code{group}. A monitor interface matches an interface of the mode
    it monitors, of the same \code{group} when it monitors a system or mirrored-system
    interface. Only initiators and targets are picked automatically, the other modes
    need the exact, named call. There is no need to say which side is the initiator and
    which is the target: each side's mode is already set on its own component, so this
    importer reads it instead of asking the script to repeat it.
    \item If exactly one matching pair exists, it is used.
    \item If more than one exists, \code{connect\_bus} raises \code{ValueError} listing
    every candidate interface name on both sides. The caller must then say exactly which
    one to use, by passing \code{a.bus("...")}/\code{b.bus("...")} for at least one side.
    A multi-port interconnect (several identical initiator interfaces, one per attached
    peripheral) will usually hit this case; it is expected, not an edge case.
    \item If none matches, \code{ValueError} explains why (no shared bus definition, no
    opposite mode available, different system groups, or every candidate already used)
    and lists what bus interfaces are still free on each side.
\end{enumerate}

On success, one \code{ipxact.Interconnection} is added to the design, with
\code{active\_interface} set from \code{a}'s side and \code{other\_active\_interfaces=[<b's
side>]}. Its name always follows the same pattern, \code{<instance a>\_to\_<instance b>},
built from the two instance names even when an interface is named with \code{.bus(...)} (a
number is added at the end if that name is already taken, e.g.\ a second link between the
same two instances). Both interfaces are now marked used, so a later
\code{connect\_bus()} call will not reuse them.

When one side is a monitor, an \code{ipxact.MonitorInterconnection} is added instead.
Only the monitor interface is marked used: the interface it watches stays free for a
normal connection.

\subsubsection{Address mapping}
\label{sec:address-mapping}

\code{base\_addr}/\code{size} are a convenience for the common case: a target sitting at
some offset on an addressable bus. IP-XACT actually handles this through
\code{addressSpace}/\code{segment} on the initiator side, resolved through a
\code{designConfiguration}, but \code{XactFlow} doesn't apply that yet (see the main
\code{XactFlow} README's Known Limitations). Doing this the real way is future work, once
that support exists. Until then, when either is given,
they're recorded as a vendor extension on the \emph{target} side of the connection (a
target or mirrored initiator interface). A connection with no such side, like a system
or monitor one, raises \code{ValueError}. This is the same way IP-XACT represents
anything the standard doesn't cover and isn't modeled here yet. Concretely, something to
the effect of:

\begin{lstlisting}[style=xmlblock, caption={Placeholder address-mapping vendor extension.}]
<xactflow:addressMapping baseAddr="0x40010000" size="0x1000"/>
\end{lstlisting}

is appended to that interface's \code{vendor\_extensions}. This is a placeholder, not a
standards-compliant addressing mechanism; anything reading it back needs to know to look
for it specifically. It should be revisited (and likely replaced) once \code{XactFlow}
applies \code{DesignConfiguration}/\code{addressSpace} for real.

\subsection{\texttt{connect(source, target)}}

An ad hoc, signal-level connection between exactly two ports, each a \code{PortRef}
(from \code{.port(name)} or the attribute shorthand). Unlike \code{connect\_bus}, which
leaves signal-level compatibility to \code{link()}, \code{connect} checks the ports
itself, since the check is cheap and both ports are already in hand:

\begin{itemize}
    \item Both ports must belong to this design: to its instances, or be its top-level
    ports (see Section~\ref{sec:add-port}).
    \item Directions must be compatible: one \code{out} and one \code{in}, or either side
    \code{inout}. Two \code{out}s or two \code{in}s raise \code{ValueError} naming both
    ports and their directions.
    \item A port cannot be connected to itself, and the same two ports cannot be
    connected twice.
    \item An \code{in} port can only be driven by one connection.
\end{itemize}

On success, appends one \code{ipxact.AdHocConnection} with a single
\code{InternalPortReference} pair (\code{component\_instance\_ref}/\code{port\_ref} for
each side), named
\code{f"\{source.instance.name\}\_\{source.name\}\_to\_\{target.instance.name\}\_\{target.name\}"}
(a number is added at the end if that name is already taken). A top-level port is
written as an \code{ExternalPortReference} instead, and named by its own name alone.
Bit-slice or struct-sub-port ad hoc connections (\code{SubPortReference}/\code{PartSelect}
in \code{ipxact-compiler}'s model) are out of scope for this first version;
\code{connect()} only wires whole ports to whole ports.

\subsection{\texttt{add\_port(direction, name, width=None, *, connect=None) -> PortRef}}
\label{sec:add-port}

Declares one top-level wire port: a port of the component containing the design, which
the design reaches with an \code{externalPortReference}.

\begin{itemize}
    \item \code{direction} is \code{"in"}, \code{"out"} or \code{"inout"}, seen from
    outside the component. Anything else, \code{phantom} included, raises
    \code{ValueError}.
    \item \code{name} follows the same naming rule as an instance name. It must be unique
    among the top-level ports, including the ones \code{add\_bus} creates; a duplicate
    raises \code{ValueError} naming the call that added the first one.
    \item \code{width} is \code{None} for a single bit, or a number of bits \code{N} for
    an \code{[N-1:0]} vector.
    \item \code{connect}, if given, is a \code{PortRef} connected to the new port right
    away, exactly as \code{connect(port, connect)} would.
\end{itemize}

Returns a \code{PortRef} with no instance, which \code{connect()} takes like an instance
port. Inside the design, a top-level port works the other way round from an instance
port: a top-level \code{in} port drives the instance ports it connects to, and a
top-level \code{out} port is driven by them. So \code{connect()} pairs a top-level port
with an instance port of the same direction, or an \code{inout} one, and drives a
top-level \code{out} port only once. A top-level \code{in} port can drive several instance
ports, one \code{connect()} call each. Two top-level ports cannot be connected together.

\subsection{\texttt{add\_bus(name, bus\_type, mode, *, group=None, connect=None) -> BusInterfaceRef}}

Declares one top-level bus interface: a bus interface of the component containing the
design, which the design reaches with a \code{hierInterface}.

\begin{itemize}
    \item \code{name} follows the same naming rule, and must be unique among the top-level
    bus interfaces.
    \item \code{bus\_type} is the VLNV of a bus definition, resolved against
    \code{library} right away, like \code{add\_ip}'s \code{vlnv}.
    \item \code{mode} is the interface mode, as IP-XACT writes it: \code{"initiator"},
    \code{"target"}, \code{"mirroredInitiator"}, \code{"mirroredTarget"},
    \code{"system"} or \code{"mirroredSystem"}. A \code{"monitor"} has nothing to watch
    at the top level, and raises \code{ValueError}.
    \item \code{group} is the system group: needed by a \code{system} or
    \code{mirroredSystem} mode, refused by the others.
    \item \code{connect}, if given, is connected to the new interface right away, exactly
    as \code{connect\_bus(interface, connect)} would.
\end{itemize}

Returns a \code{BusInterfaceRef} with no instance, which \code{connect\_bus()} takes like
an instance's \code{.bus(name)}. It pairs it with an instance interface of the same bus
type and the \textbf{same} mode, as the standard requires of a hierarchical connection
(SCR 2.4 to 2.10): a top-level target is an internal target, seen from outside. The
instance side can still be picked automatically. Two top-level interfaces cannot be
connected together, and \code{base\_addr}/\code{size} raise \code{ValueError}, since the
address map of a top-level interface belongs to the connection outside the component.
The \code{Interconnection} has the instance side as its \code{activeInterface} and the
top-level interface as a \code{hierInterface}, and is named from the top-level interface
name and the instance name, e.g.\ \code{ext\_if\_to\_apb\_bus}. A top-level interface is
connected only once.

A top-level interface takes its ports from the internal interface it connects to: the
abstraction types and port maps are copied, and each mapped port becomes a top-level port
named \code{<interface>\_<logical port>}, a copy of the internal one (same direction, same
width). \code{ext\_if} connected to an interface mapping the logical ports \code{CLK} and
\code{DATA} gives the top-level ports \code{ext\_if\_CLK} and \code{ext\_if\_DATA}. A name
already taken by another top-level port raises \code{ValueError}.

\subsection{\texttt{build() -> ipxact.Design}}

Returns the finished \code{ipxact.Design}: every \code{add\_ip} as a
\code{ComponentInstance} (in call order), every \code{connect\_bus} as an
\code{Interconnection} (or a \code{MonitorInterconnection} for a monitor), every
\code{connect} as an \code{AdHocConnection}. It does not
check that every bus interface got connected: an unconnected optional interface (e.g.\ an
unused debug port) is a legitimate, common design, not an error. Completeness is
\code{SCR}'s concern, if and when a rule for it exists, not this importer's.

\subsection{\texttt{build\_component() -> ipxact.Component}}

Returns the \code{ipxact.Component} containing the design: every top-level port, those of
\code{add\_port} and those \code{add\_bus} created, every \code{add\_bus} interface, and
one view, \code{hierarchical}, whose \code{designInstantiation}
(\code{hierarchical\_design}) refers to the design. \code{xactflow.link()} finds the
component through that view, and checks the \code{hierInterface} and
\code{externalPortReference} elements against it. A script with no top-level port or bus
interface still gets this component, with the view only.

Scripts don't call \code{build()} or \code{build\_component()} themselves. The importer
does, after running the script, see below.

\section{How the importer runs a script}

\begin{lstlisting}[style=pyblock, caption={The \texttt{Importer} entry point.}]
class ArchiDescImporter(xactflow.Importer):
    def import_(self, source: Path, library: xactflow.Library, **options) -> None: ...
\end{lstlisting}

It executes \code{source} as a plain Python file (\code{runpy.run\_path}), then looks for
a module-level variable named \code{design}, of type \code{Design}. Missing or
wrong-typed \code{design} raises \code{ValueError} naming what was expected. It then
calls \code{.build\_component()} and \code{.build()} on it and adds both results to
\code{library} as targets (\code{library.add(document, source, replace=True,
target=True)}), which is what an exporter writes. They are regenerated from the script on
every run, so they replace the documents with the same VLNVs already in \code{library},
e.g.\ its previous output scanned from a \code{-{}-lib} folder. The script still builds
its own \code{Design} on its own \code{Library}: \code{library} is where the results go,
and where an exporter run after the importer looks up the components the design
instantiates.

\section{Worked example}

\begin{lstlisting}[style=pyblock, caption={A complete design description, linked in the same script.}]
from xactflow import Library, link
from xactflow_archidesc import Design

library = Library.scan("path/to/ip/library")
design = Design("cern.ch:soc:example:0.1", library)

cpu   = design.add_ip("cpu",   "openhwgroup:core:ibex:1.0", transforms=["tmrg"])
uart  = design.add_ip("uart",  "cern.ch:ip:uart:1.0", parameters={"BAUDRATE": 115200})
timer = design.add_ip("timer", "pulp:ip:timer:1.0")
debug = design.add_ip("debug", "cern.ch:ip:debug_module:1.0")
bus   = design.add_ip("apb_bus", "cern.socgen:ip:apb_rt:0.1.0")

design.connect_bus(cpu, bus.bus("s0"))
design.connect_bus(bus.bus("m0"), uart,  base_addr=0x4001_0000, size=0x1000)
design.connect_bus(bus.bus("m1"), timer, base_addr=0x4002_0000, size=0x1000)

design.connect(debug.debug_req_o, cpu.debug_req_i)
design.connect(cpu.debug_resp_o, debug.debug_resp_i)

design.add_port("inout", "jtag_io", connect=debug.jtag_io)
design.add_port("out", "irq_o", connect=uart.irq_o)

library.add(design.build_component())
linked = link(design.build(), library)
\end{lstlisting}

The interconnect has several identical ports on each side, so each
\code{connect\_bus} call names the one to use with \code{.bus(name)}.

\code{design.build()} produces the \code{ipxact.Design}
\code{cern.ch:soc:example.design:0.1}: 5 \code{ComponentInstance}s, 3
\code{Interconnection}s (\code{cpu\_to\_apb\_bus}, \code{apb\_bus\_to\_uart},
\code{apb\_bus\_to\_timer}, one per \code{connect\_bus} call), and 4
\code{AdHocConnection}s, 2 of them to the top-level ports. \code{design.build\_component()}
produces the \code{ipxact.Component} \code{cern.ch:soc:example.component:0.1} containing
it, with the top-level ports \code{jtag\_io} and \code{irq\_o}. With that component added
to the same \code{library}, \code{link()} resolves and checks the design exactly as it
would a hand-written or hand-exported one, top-level ports included, all in this one
script, with no separate importer step needed. Running the same script through
\code{ArchiDescImporter} instead (letting the CLI or another tool drive it) does the same
\code{build\_component()} and \code{build()} calls automatically and adds both results to
the library it is given; linking is then up to whatever exporter reads that library, not
shown here.

\section{Requirement on imported components}
\label{sec:relationship-sv}

\code{add\_ip}'s \code{parameters} argument only works for a component whose parameters
carry a \code{parameterId}; that's what \code{config\_element\_values} keys by. Any
component supplied to this format, whether produced by \code{XactFlow-sv}, another
importer, or hand-written IP-XACT, needs \code{parameterId} and \code{resolve="user"} set
on each parameter meant to be overridable this way. One with no \code{parameterId} cannot
be referenced for override at all, and one with \code{resolve="immediate"} cannot be
modified through configuration, per the standard. This is a general requirement on the
components this format consumes, not something specific to one importer.

\section{Open questions, deferred rather than silently resolved}

Things this first version leaves open, on purpose:

\begin{itemize}
    \item \textbf{Hierarchical design description.} A sub-design instantiated as a
    component inside a bigger one is not addressed here; this format describes one level:
    a design, and the top-level ports and bus interfaces of the component containing it.
    \code{XactFlow}'s own linker doesn't recurse into nested
    designs yet either (see its README's ``One level of hierarchy''
    limitation), so there is nothing downstream to hand a hierarchical result to yet
    regardless.
    \item \textbf{Address mapping}, as above: a real system, not a vendor-extension
    placeholder, once \code{XactFlow} applies
    \code{DesignConfiguration}/\code{addressSpace}.
    \item \textbf{Top-level ports copied from part of a port}: a top-level bus interface
    copies whole internal ports. A port map onto part of an internal port (a
    \code{partSelect} or sub-port) would need a top-level port of just that part, and is
    refused until that is designed. A copied port also keeps its width as written, which
    can refer to a parameter of the internal component that the component containing the
    design does not have; that needs the width evaluated first.
    \item \textbf{Protocol bridges} (e.g.\ an APB-to-OBI adapter between two incompatible
    bus segments): not addressed. \code{connect\_bus} either finds a matching pair or
    fails; nothing here automatically adds a bridge component. A bridge, if one exists as
    a real component, is just another \code{add\_ip} the script author wires in
    explicitly on both sides, sourced and placed by the user, not made automatically by
    the tool.
    \item \textbf{System/mirrored/monitor interface modes}: real IP-XACT concepts,
    deliberately not auto-matched by \code{connect\_bus} in this first version (see
    above).
    \item \textbf{Bus type parameter values}: \code{connect\_bus} compares the parameter
    values set on each side's bus type (a data width, for example), not just the bus VLNV.
    These values are raw expressions (\code{"32"} and \code{"0x20"} are equal, a value can
    refer to an instance parameter), so they have to be evaluated before they can be
    compared. This first version only compares the bus VLNV, until \code{XactFlow}
    evaluates parameter values well enough to do it.
\end{itemize}
